# Протокол A/B до запуска

Задачи относятся к учебному трекеру. Сравниваются две конфигурации одного runtime. A запускается без каталога, инструкций и загрузчика скиллов. B получает каталог из `skills/` и может вызвать `load_skill` для подходящей работы. Оба варианта получают одинаковые обычные инструменты и один MCP-сервер `tracker` с фиксированным снимком `src/mcp/tasks.json`.

**Гипотеза.** B даст больше корректных артефактов суммарно в двух сценариях для скиллов и не ухудшит результат в контрольном сценарии. Дополнительное ожидание — загрузка инструкций увеличит средний расход входных токенов. Итог считаем по всем попыткам, включая ошибки, таймауты и остановки по лимиту. Малая выборка относится только к выбранным задачам и настройкам.

## Фиксированные условия

- Модель Ollama `workbench-qwen3:4b` на основе `qwen3:4b`, контекст 8192. Настройка в `config/Modelfile.eval`.
- OpenAI-compatible endpoint `http://127.0.0.1:11434/v1/`. Температура 0.2, `reasoning_effort=none`, максимум 1024 выходных токена, таймаут запроса 90000 мс. Seed отсутствует.
- Режим `auto` в обеих версиях. Лимиты одного запуска составляют 12 запросов модели, 24 вызова инструментов, 8 действий с эффектом и 64 000 байт результатов. Policy в `eval/fixtures/policy.json` защищает исходные файлы и запрещает Bash в обоих вариантах.
- Каждая попытка получает новую временную директорию, отдельное состояние, новую сессию и `run_id`. Файл результата до запуска отсутствует. Снимок MCP неизменяемый, соединение открывается заново. Сохраняются все 18 попыток в порядке A1, B1, A2, B2, A3, B3 для каждого сценария.
- До первой попытки `manifest.json` фиксирует модель, параметры, запросы, порядок, список проверок и SHA-256 источников, policy, MCP, скиллов, проверок, рабочего runtime и `package-lock.json`. Повторная сверка после последнего запуска подтверждает неизменность.

## Сценарии и критерии

| Сценарий     | Исходные данные                                           | Проверка артефакта                                                                                                       | Выбор в B                 | Обязательные успешные вызовы в порядке                |
| ------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------- | ----------------------------------------------------- |
| `open-tasks` | Пять задач read-only MCP                                  | `open-tasks.md` содержит Markdown-таблицу ID и названий трёх открытых задач, по возрастанию ID                           | `open-task-report`        | `mcp_tracker_list_tasks`, `write_file` для результата |
| `progress`   | `progress.json` с шестью занятиями, включая незавершённые | `progress-summary.md` учитывает всех учащихся, суммирует только завершённые занятия и содержит корректную строку «Итого» | `progress-summary`        | `read_file` исходника, `write_file` для результата    |
| `no-skill`   | Текстовая заметка `note.txt`                              | `evidence.txt` побайтно совпадает с исходником                                                                           | Ни одной попытки загрузки | `read_file` исходника, `write_file` для результата    |

Каждый сценарий определяет допустимые вспомогательные чтения, схемы проверок и одинаковый запрос в `eval/cases.ts`. Точные ожидаемые данные и проверки хранятся в `eval/checks/` вне workspace. Исходные файлы должны сохраниться, лишние файлы запрещены. В таблицах допустимы заголовок перед таблицей, разное выравнивание и промежутки, в сводке прогресса допустим любой порядок учащихся перед итогом.

`outcome_pass` оценивает фактический артефакт. `tool_pass` оценивает допустимость вызовов и успешные обязательные действия по журналу. `routing_pass_or_na` в B требует загрузки нужного скилла без попыток вызвать посторонний. В A показатель неприменим. Полный зачёт попытки требует `completed`, трёх применимых положительных проверок и отсутствия итоговой ошибки. Гипотеза оценивается по `outcome_pass`. Входные и выходные токены берутся из usage модели. Средние по полно известным попыткам сопровождаются количеством полных, частичных и неизвестных попыток.

## Воспроизведение

```bash
ollama pull qwen3:4b
ollama create workbench-qwen3:4b -f config/Modelfile.eval
npm ci
npm run build
env -u OPENAI_SEED AGENT_PROVIDER=ollama OPENAI_BASE_URL=http://127.0.0.1:11434/v1/ \
  OPENAI_API_KEY=ollama OPENAI_MODEL=workbench-qwen3:4b OPENAI_TEMPERATURE=0.2 \
  OPENAI_REASONING_EFFORT=none OPENAI_MAX_TOKENS=1024 OPENAI_TIMEOUT_MS=90000 \
  node dist/eval/index.js run .agent/eval-reproduction
node dist/eval/index.js report .agent/eval-reproduction
```

Команда `smoke <сценарий> <A|B> [каталог]` проверяет одну независимую пробную попытку. Она пишет отдельный manifest с отметкой `smoke` и не входит в 18 основных попыток.
