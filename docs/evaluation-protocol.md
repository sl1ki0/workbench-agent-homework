# Протокол A/B до запуска

Задачи относятся к учебному трекеру. Сравниваются две конфигурации одного runtime. A запускается без каталога, инструкций и загрузчика скиллов. B получает каталог из `skills/` и может вызвать `load_skill` для подходящей работы. Для одного и того же сценария обе версии получают одинаковые рабочие инструменты, MCP и исходные данные.

**Гипотеза.** B даст больше корректных артефактов суммарно в сценариях для скиллов и сохранит качество в контрольном сценарии. Дополнительное ожидание — загрузка инструкций увеличит средний расход входных токенов. Учитываются все попытки, включая ошибки, таймауты и остановки по лимиту.

## Фиксированные условия

- Провайдер Ollama через OpenAI-compatible endpoint `http://127.0.0.1:11434/v1/` или другой настроенный совместимый API. До первого trial манифест сохраняет фактический идентификатор выбранной модели, температуру, режим reasoning, лимит ответа и таймаут. Эти параметры общие для A и B. Их изменение требует нового каталога серии.
- Режим `auto` в обеих версиях. Бюджет попытки включает 12 запросов модели, 24 вызова инструментов, 8 действий с эффектом и 64 000 байт результатов. Policy из `eval/fixtures/policy.json` защищает исходные файлы и запрещает Bash.
- Каждая попытка использует чистый workspace, отдельное состояние, новую сессию и `run_id`. Соединение с MCP открывается заново. Порядок для каждого сценария A1, B1, A2, B2, A3, B3. Базовый набор содержит 18 попыток, расширенный — 30.
- До первой попытки `manifest.json` фиксирует модель, параметры, запросы, порядок, проверки и SHA-256 источников, policy, серверов MCP, скиллов, рабочего runtime и `package-lock.json`. Возобновление проверяет совпадение манифеста и пропускает сохранённые попытки. После завершения проверяются контрольные суммы.

## Сценарии и критерии

| Сценарий           | Исходные данные                                                                         | Проверка артефакта                                                                                    | Выбор в B          | Обязательные вызовы в порядке                                               |
| ------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------ | --------------------------------------------------------------------------- |
| `open-tasks`       | Пять задач read-only MCP                                                                | `open-tasks.md` содержит таблицу ID и названий трёх открытых задач по возрастанию ID                  | `open-task-report` | `mcp_tracker_list_tasks`, `write_file` результата                           |
| `progress`         | `progress.json` с шестью занятиями                                                      | `progress-summary.md` учитывает всех учащихся, только завершённые занятия и корректную строку «Итого» | `progress-summary` | `read_file` исходника, `write_file` результата                              |
| `no-skill`         | Текстовая заметка `note.txt`                                                            | `evidence.txt` побайтно совпадает с исходником                                                        | Без скилла         | `read_file` исходника, `write_file` результата                              |
| `mcp-failure`      | Отдельное read-only SDK-соединение, инструмент стабильно отвечает `TRACKER_UNAVAILABLE` | `tracker-status.md` сообщает об ограничении и не содержит выдуманного списка или количества           | `open-task-report` | `mcp_tracker_list_tasks` с зафиксированной ошибкой, `write_file` результата |
| `progress-variant` | У завершённого занятия L5 отсутствует продолжительность                                 | `progress-summary.md` включает всех учащихся, считает известные минуты и явно отмечает пропуск L5     | `progress-summary` | `read_file` исходника, `write_file` результата                              |

Каждый сценарий определяет допустимые вспомогательные чтения, схемы проверок и одинаковый запрос в `eval/cases.ts`. Точные ожидаемые данные и проверки хранятся в `eval/checks/` вне workspace. Исходные файлы должны сохраниться. В таблицах допустимы заголовок перед таблицей, разное выравнивание и промежутки. В сводке прогресса допустим любой порядок учащихся перед итогом.

`outcome_pass` оценивает фактический артефакт. `tool_pass` оценивает допустимость и ожидаемый исход обязательных вызовов по журналу. `routing_pass_or_na` в B требует загрузки нужного скилла без попыток вызвать посторонний. В A показатель неприменим. Полный зачёт попытки требует `completed`, трёх применимых положительных проверок и отсутствия итоговой ошибки. Гипотеза оценивается по `outcome_pass`. Входные и выходные токены берутся из usage модели. Средние по полному usage сопровождаются количеством полных, частичных и неизвестных попыток.

## Воспроизведение

Перед запуском настройте `.env` по `.env.example`. Расширенный набор запускается одной командой после сборки.

```bash
npm ci
npm run build
npm run eval -- extended .agent/eval-reproduction
npm run eval -- resume .agent/eval-reproduction
npm run eval -- report .agent/eval-reproduction
```

Используйте `resume` после прерывания. Команда восстанавливает индекс по атомарно сохранённым результатам и выполняет оставшиеся trials. `run <каталог>` запускает базовые 18 попыток, а `smoke <сценарий> <A|B> [каталог]` сохраняет отдельную пробу вне основной серии.
